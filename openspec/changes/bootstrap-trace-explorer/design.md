# Design

## Context

See `proposal.md` for the motivation. The repository is new. Its first commit supplies a Rust HTTP server, a web client starter and a health endpoint. Import and analysis are proposed work.

The upstream TypeScript extension records Pi events as JSONL; a Python renderer builds a static HTML report. The compatibility baseline is commit `5441bcca041e3b3a203aee91c68e8ea809e6aa27`. Pi extensions run in JavaScript or TypeScript, so a Rust rewrite initially imports the collector's files. An RPC adapter would be a separate source with different capture fidelity.

## Goals / Non-Goals

**Goals:** Keep one owner of trace semantics, expose a small versioned HTTP presentation contract and support a clear local investigation workflow. Make source uncertainty and incomplete measurements visible.

**Non-Goals:** No database, watcher, hosted service, native window, custom collector, plugin framework or benchmark claims in this change. The startup health route does not imply trace routes are implemented.

## Decisions

### Local Rust service with a web client application

Use Axum and Tokio for a loopback service, a compiled web client and TypeScript for interaction, and Vite for development and static assets. A production build is served from the Rust process with the same origin. Development uses Vite on port 5173 with an `/api` proxy to Rust on port 4317. Initial assets are read from `web/dist`; release asset embedding is separate packaging work.

The caller's proposed product command is `pi-trace serve ./trace-directory`. Import finishes before serving an immutable snapshot. This command is planned; the current scaffold starts with `cargo run -p pi-trace --locked` and accepts no trace input.

We compared a local service with a standalone HTML report generated by a Rust CLI. Both keep semantics in Rust. The service is the base because queries and large views stay behind a small API rather than loading the entire dataset into the browser. A separate architecture reviewer agreed. From the report candidate we adopted versioned presentation data and explicit content inclusion. Static report export remains a later change.

### One immutable trace owns interpretation

The future `crates/trace-core` will expose one import operation and queryable domain views. Private importer code owns wire records and correlation maps. The normalized graph stores occurrence identifiers, parent links, source provenance and diagnostics. Indices support hierarchy, timeline windows and tool lookup. The HTTP server converts views into versioned response types; web client never reinterprets upstream events.

Proposed Rust usage, not a current API:

```rust
let trace = Trace::open(source, ImportLimits::default())?;
let overview = trace.overview();
let spans = trace.timeline(query);
let detail = trace.node(node_id);
```

`Trace::open` returns `Result<Trace, ImportError>`. Query methods operate on immutable data. `node` returns an optional view for a snapshot-local identifier. Domain identifiers distinguish session epochs, turn attempts and node occurrences. HTTP identifiers are opaque strings to avoid JavaScript integer precision loss. Durations carry recorded, derived or unknown provenance and their measurement meaning.

`session_start` opens a new epoch. Repeated turn starts create distinct attempts. Tool correlation uses occurrence identity and `toolCallId`; explicit child IDs own child linkage. Ambiguities remain diagnostics. Generation usage is authoritative when present; the turn summary is a fallback only when generation usage is absent. Partial step coverage remains incomplete.

### Small presentation API

The bootstrap implements only `GET /api/v1/health`, returning `status`, `name`, `version` and `stage`.

Planned routes are `GET /api/v1/overview`, `GET /api/v1/timeline`, `GET /api/v1/nodes/{id}` and `GET /api/v1/diagnostics`. Content reveal will require a distinct request for bounded node content. Metadata responses omit prompt, argument and result bodies. Metadata itself can contain sensitive names or paths and is not a sanitized export.

The CLI selects one source at startup; there is no arbitrary-path HTTP parameter. Host and Origin validation is required before trace routes ship. The server must enforce loopback hosts and same-origin requests, with a development origin explicitly allowed through the Vite proxy. CORS is not opened globally.

### Bounded import and previews

Start with limits of 128 MiB total input, 1 MiB per record, 100,000 records and 8 KiB per revealed field. These are policy limits to validate with synthetic fixtures, not measured performance guarantees. Read bounded records before JSON decoding and reject limit breaches explicitly. Resolve sources under the selected root and reject escaping symlinks.

Unknown types, malformed middle lines, incomplete final lines and missing end events remain distinct diagnostics. Raw log bodies are untrusted text. Revealed content is rendered with escaped text bindings; no HTML injection or external asset URLs come from a trace.

### Investigation layout

Use a compact toolbar for source, search and filters; a hierarchy rail on the left; a timeline in the center; and a details panel on the right. One selection drives all views. Timing labels describe what was measured. Error state and selection use text and icons in addition to color. On narrow windows the panels stack while selection persists. The bootstrap screen proves connectivity only and is not a mock trace explorer.

## Risks / Trade-offs

- Raw recordings can expose private content → explicit reveal, bounded previews, synthetic fixtures and no external requests; no blanket redaction claim.
- Wall-clock jumps and missing events can distort timelines → typed timing provenance and visible diagnostics.
- Snapshot import does not update while Pi runs → explicit restart/reload workflow; a watcher needs a later design.
- Assets are not embedded in the bootstrap binary → document the build order and keep release packaging tracked separately.
- Size limits do not establish interaction speed → measure a fixed synthetic workload before publishing performance claims.

## Migration Plan

There is no existing installation or stored database to migrate. Land and verify the scaffold, then implement import, analysis and explorer as successive slices. Keep the change active until its behavior scenarios pass. A scaffold commit can be reverted without modifying trace sources.
